# 通信経路と障害調査の範囲

2026-10-31のコード・保存済み通信ログ・稼働設定の調査。Android 1.70.65で修正した実装上の問題と、実機での再現確認が必要な問題を区別します。個別の通信環境での障害がすべて解消したことを示す文書ではありません。

## 通信経路

| 操作 | 経路 | 通信の管理 |
|---|---|---|
| 設定・履歴・認証・サーバー経由の生成 | `PlaygroundApi` → 接続先のHTTPS → Apache → Gunicorn/Flask → 必要に応じてDB・Redis・RQ | Cookieを使わないBearer認証。通常通信・回答受信・アップロード・接続確認は別の実行キュー。通常のGETだけ接続障害の自動回復を許す |
| サーバー不使用モードの生成 | `DirectHttp` → AI事業者 | 当サイトのプロキシ・認証・ワーカーを経由しない。回答ストリームとその他の通信は別の実行キュー。生成POSTを接続エラーで自動再送しない |
| 更新の確認・APK取得 | GitHub API／Release → GitHub配布用CDN | アプリのAPI用キューとは独立。SHA-256取得、APK取得、サイズ・ハッシュ検証、保存の順。HTTPリダイレクトがある |
| DNS補助 | AndroidのDNSが失敗した場合だけ、許可したホストをCloudflare／GoogleのDoHへ問い合わせ | 独立したHTTPクライアント。認証情報を送らない。通常APIが成功するまでの再送機構とは別 |
| 未送信フィードバック・同期・管理者診断 | それぞれ別の `PlaygroundApi` インスタンス → 接続先 | アプリの実行キューは独立していても、端末の回線は共用する |

公式サイトの公開経路にはCloudflareがあります。WebブラウザーとAndroidのHTTP方式・接続再利用が同一とは限りません。サーバーからの接続確認だけで端末側の経路を再現したことにはなりません。

## 確認できた実装上の問題

### 長時間の受信と通常通信の実行キューの共有

`OkHttpClient.newBuilder()` は実行キューも引き継ぎます。HTTP/1.1にするだけではキューは分離されません。既定の同一ホスト5件が回答ストリームの読み取りで埋まると、設定取得や停止操作も順番待ちになります。待ち行列にいる間はOkHttpの `callTimeout` の計時も開始していません。

1.70.65ではサーバー経由・事業者直接通信とも回答受信のDispatcherと接続プールを分離しました。5本を開いたまま、通常APIや生成停止を実行する回帰テストがあります。実際の障害がすべてこの条件だったことは確認できていません。

仕様の根拠: [OkHttp 5.3.0 Dispatcher](https://github.com/square/okhttp/blob/parent-5.3.0/okhttp/src/commonJvmAndroid/kotlin/okhttp3/Dispatcher.kt)、[RealCall](https://github.com/square/okhttp/blob/parent-5.3.0/okhttp/src/commonJvmAndroid/kotlin/okhttp3/internal/connection/RealCall.kt)。

### APKの本文読み取り中のキャンセル

以前は応答ヘッダー取得のコルーチンが終わった後、本文のブロッキング読み取りをキャンセルしても直ちにソケットへ伝わりませんでした。再試行が前の処理の終了待ちになる問題です。1.70.65では本文を読み終わるまでキャンセル監視を維持し、途中で使われなくなった応答も閉じます。途中まで受信して次のバイトが来ない状況をテストします。最初の接続失敗の原因とは別です。

### サーバーの配信期限と購読解放

`pubsub.listen()` の戻りを待つループ内だけで期限を確認していたため、通知がないと600秒の期限も確認できませんでした。また、最初のジョブIDや蓄積済み回答の配信中に切断すると、後半の `finally` に到達しませんでした。

通常送信と再接続の両方で、期限内の短いポーリングと約15秒ごとの空行へ変更しました。購読は初回の配信も含めて管理し、正常終了・例外・切断で閉じます。空行は既存のWeb・Androidクライアントが読み飛ばすため、回答本文を変更しません。これはサーバーの処理枠を保持し続ける条件の修正であり、過去の障害時に処理枠が枯渇していたと断定するものではありません。

### サーバー処理時間から認証が抜けていた

以前の `server.request.end.ms` はAndroidのBearer検証後に計時を開始していました。この値が短くても、認証のDB待ち・それより前の受付待ちは除外できません。最初のアプリケーションフックで時計を取り、同意確認後の `server.request.start.ms` と全体の `server.request.end.ms` を記録するようにしました。受付前やプロキシ内の時間は依然として別です。

## 調べた項目と判断の限界

| 項目 | 確認結果・限界 |
|---|---|
| モバイル通信の禁止・特定回線への固定 | APK・設定・生成をWi-Fiだけに制限する分岐、プロセスやソケットを特定ネットワークへ固定する処理はない。モバイル許可設定はオフラインキャッシュの全件同期用 |
| IPv4／IPv6 | OkHttp 5.3.0のFast Fallbackは有効。単純に「IPv6しか試さない」とは説明できない。調査サーバーにはIPv6の既定経路がなく、そこからのIPv6失敗を端末や公開サイトの障害判定に使えない |
| TLS・認証情報 | システムの証明書検証を使用。回線別に検証を無効化する処理はない。設定・モデル通信とAPKは認証も配布元も異なる |
| Android認証・CSRF・BAN・レート制限 | Bearer専用経路・許可メソッド・Cookieとの分離を確認。調査したApache記録ではAndroid全体への403・429拒否を確認できなかった。CDNで遮断されてサーバーへ来ない要求までは除外できない |
| Apache | 実稼働のHTTPS転送・Android用Include・エラーJSON維持・660秒のプロキシ期限・リクエスト本文の時間制限解除を確認。本文の受け渡し失敗の記録はあるが、端末の中断と独立したサーバー原因をその記録だけで区別できない |
| Gunicorn・RQ・メモリ | Gunicorn 2ワーカー×8スレッド、RQ 2ワーカー。調査時にサービスは稼働し、短い公開APIの反復取得は正常。過去のSIGKILL記録はあるが、メッセージの「Perhaps out of memory」だけでOOMとは断定できない。再現時の占有状況は過去ログから確定できない |
| 公開HTTP経路 | AndroidのUser-AgentでHTTP/1.1、ブラウザーのUser-AgentでHTTP/1.1・HTTP/2の小さなAPI応答を取得できた。GitHub配布先へのリダイレクトも有効。端末の回線での成功を保証する試験ではない |
| 過去の長時間通信 | DNS補助失敗だけでなく、要求ヘッダー送信開始後の長い待機、送信前の待機、本文送信・応答待ちの失敗が混在。共有キューやDNSだけに一本化できない |
| 既存修正 | 1.70.63の未送信フィードバックの恒久エラー停止・バックオフ、1.70.62のアップロード分離・応答待ち延長を確認。別の通信経路の失敗まで説明したことにはならない |
| ログ収集自体 | 操作ログの書き込みは専用の実行スレッド。保存・期限切れ処理には共有ロックがあるため負荷がゼロとはいえないが、過去の数十秒の通信遅延をそのロックのせいと断定する証拠はない |

## 次のログで判断できること

Androidの `http.reason_code: 111` は実行キュー、101はDNS、102はTCP、103はTLS、105〜108は送受信です。APKは `app_update.state` の200〜203で検証情報・APK・ハッシュ照合・保存を区別します。サーバーの認証前処理と配信の開始・終了は [ログ仕様](../../deploy/LOGGING.md) に記載しています。

同じ要求の端末 `parent_op` と応答の診断IDを突き合わせ、端末内の順番待ち、接続、要求の送受信、サーバー前処理、API本体、配信終了を分けます。別端末の時計同士を差し引くと時計のずれが入るため、各側の経過時間を優先します。旧ログで欠けている段階や、端末・携帯網・CDN内部でしか観測できない情報を推測で補完しません。
