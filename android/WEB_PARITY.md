# Web版との機能・デザイン一致ロードマップ

## 1. この文書の目的

公式Androidクライアントを、Web版と同じアカウント・データ・主要機能・視覚的なブランドを持つネイティブアプリへ発展させるための継続資料です。新しい作業セッションで「AndroidクライアントをWeb版と同じ機能、デザインにして」と依頼された場合は、本書を進捗の正本として使い、差分調査だけで作業を終えず、未完了項目の実装・検証・配布まで進めます。

通信・認証・署名・サーバー設定の正本は [`../deploy/ANDROID_CLIENT.md`](../deploy/ANDROID_CLIENT.md)、Web／Android同期の作業規則は `~/docs/android_sync.md` です。本書は機能とデザインの到達目標、現在地、実装順を管理します。

## 2. 目標の解釈

「同じ」はWebのHTMLをそのまま表示する意味ではありません。チャット、履歴、設定、モデル固有機能などの結果と主要な操作を一致させ、Web版の色、階層、用語、状態表示、情報量をAndroidの操作体系へ置き換えます。

- 主画面をWebViewで包まず、Kotlin／Jetpack ComposeのネイティブUIを維持する。
- ログイン、2FA、端末連携承認など、Webで安全に完了させる設計済みの認証フローはCustom Tabsを使ってよい。
- Androidの戻る操作、共有シート、Photo Picker、通知、アクセシビリティ、画面サイズへの適応は、Webと見た目を完全複製するよりプラットフォーム標準を優先する。
- APIキー、Cookie、サーバー秘密情報をAndroidへ渡して機能を再現しない。必要な機能は権限を限定したネイティブAPIとして設計する。
- Androidで合理的に提供できない管理者専用・ブラウザー専用機能は、理由と安全なWeb導線を本書に記録する。未実装のまま黙って省略しない。

## 3. 完了条件

機能・デザイン一致は、次の条件をすべて満たした状態です。

1. Web版の利用者向け機能を棚卸しし、本書の各項目が「完了」「Web導線として完了」「対象外（理由記載）」のいずれかになっている。
2. 同じアカウント、スレッド、メッセージ、添付、モデル設定について、WebとAndroidのどちらで変更しても他方で矛盾なく確認できる。
3. 通常チャットだけでなく、対象モデルの入力設定、生成結果、エラー、停止、再接続、履歴表示が一致する。
4. Web版のデザイントークンと主要画面の構造をComposeに定義し、ライト／ダーク、文字拡大、縦横画面、スマートフォン／タブレットで破綻しない。
5. ローディング、空状態、オフライン、期限切れ、BAN、Turnstile、メンテナンス、レート制限を誤解のない文言で表示する。
6. TalkBack、タップ領域、コントラスト、フォーカス、選択可能テキスト、システムの「戻る」を確認する。
7. Android単体テスト、API回帰テスト、lint、debug／release APK、固定署名照合、主要フローの実機確認を完了する。
8. `version.properties`、本書、`README.md`、`../deploy/ANDROID_CLIENT.md`、GitHub Releaseの内容が実装と一致する。

## 4. 現在の基準

基準版はAndroid 1.1.1、Web V4.8.981です。現在のAndroid版はネイティブですが、Web版との完全一致には未到達です。

状態の意味：

- **完了**：基本フローをネイティブ実装し、自動テストまたはActionsで検証済み。
- **一部**：基本機能はあるが、Web固有の操作、表示、設定の一部がない。
- **未実装**：Androidに相当機能がない。
- **Web導線**：Android内で完結せず、認証済みブラウザーへ案内する。

## 6. デザイン差分

| 項目 | 現在 | 到達目標 |
|---|---|---|
| ブランド | Web版のティール、背景、パネル、境界、状態色をComposeのライト／ダーク配色へ集約 | 角丸、影、状態別トークンも共通化 |
| 画面構造 | TopAppBar、履歴Drawer、会話、Composer | Webのサイドバー、メインステージ、入力部の情報階層を端末幅に適応 |
| テーマ | システムのライト／ダーク | Webのテーマ選択とアカウント設定を同期し、システム設定も選択可能にする |
| タイポグラフィ | Material標準 | 日本語・コード・数式を含むWeb版相当の階層、行間、可読性を定義 |
| アイコン | 文字記号とテキストボタン中心 | 統一したMaterial Symbolsまたはアプリ内vectorを使用し、内容説明を付ける |
| メッセージ | 単純なカード | Webの役割、思考、添付、ツール、エラー、進捗を区別する表示へ拡張 |
| 入力欄 | モデル、添付、送信、停止 | Webのコンテキストバー、設定、候補、進捗を段階表示し、狭い画面で整理 |
| 動き | 基本Compose遷移 | reduce motionを尊重し、送受信・Drawer・モーダルの一貫した遷移を定義 |
| タブレット | 専用構成なし | 2ペイン表示を基本とし、履歴と会話を同時表示 |
| アクセシビリティ | 未監査 | TalkBackラベル、48dp以上の操作領域、コントラスト、文字拡大を検証 |

デザインを実装するときは、Webの巨大な結合済みJSを読まず、`templates/chat/README.md` から対象HTMLを選び、見た目は最新版の `static/css/chat.custom.v*.css` の該当セレクタだけを調べます。動作は `static/js/chat_core_parts/README.md` で担当部品を特定してから必要箇所だけを読みます。

## 7. 推奨実装順

### Phase 1：チャット体験とデザイン基盤

1. Webの色・寸法・タイポグラフィをComposeのDesignSystemへ集約する。
2. 安全なMarkdown、コード、リンク、引用、数式、添付プレビューを実装する。
3. モデルメタデータとモデル別設定をAPI化し、選択画面とComposerを一致させる。
4. メッセージ操作、エラー、空状態、進捗、オフライン復帰を整える。
5. スマートフォンとタブレットのナビゲーションを分ける。

### Phase 2：履歴・添付・設定

1. スレッド設定、ブックマーク、一時チャット、分岐、PDF出力を実装する。
2. アップロード進捗、キャンセル、プレビュー、カメラ、チャンクアップロードを実装する。
3. ファイルライブラリ、Gems、一般設定、セッション管理を実装する。
4. Webでのみ扱う秘密情報や高度なセキュリティ設定には、明確なWeb導線を用意する。

### Phase 3：高度な生成機能

1. Batchと完了通知を実装する。
2. 画像、動画、音楽、OCR、TTS、STSをモデル別に実装する。
3. MCP、Coding、Canvas、Python結果を構造化表示する。
4. リアルタイム音声・音楽をAndroidの音声ライフサイクルに合わせて実装する。

各Phaseは巨大な一括変更にせず、独立して利用できる単位で版を上げ、Actionsと実機確認を行います。ただし、一つの機能についてサーバーだけ、またはAndroidだけを未整合のまま公開しません。

## 8. 作業セッションごとの進め方

1. 本書と `~/docs/android_sync.md` を読む。
2. 対象機能をWeb側の分割READMEで特定し、関係するファイルだけを読む。
3. 現行APIで安全に実装できるか確認する。設定・秘密情報APIをそのままBearerへ開放しない。
4. 必要ならAndroid専用API、サーバー回帰テスト、Compose UI、Android単体テストを同じ作業で実装する。
5. 対応する本書の行とデザイン差分を更新する。完了していない項目を「完了」にしない。
6. Androidを変更したら `VERSION_CODE` と `VERSION_NAME` を更新する。
7. Web側の通常リリース検証・公開とAndroid Actionsを完了し、固定署名、artifact、GitHub Releaseを確認する。
8. 実機未確認の項目は明記し、確認済みと推測を区別する。

## 9. 検証マトリクス

機能追加ごとに、該当する行をテスト対象へ含めます。

| 観点 | 必須確認 |
|---|---|
| アカウント | 通常、2FA、暗号化設定、失効、期限切れ、BAN、Turnstile |
| 通信 | Wi-Fi切替、タイムアウト、429、503、途中EOF、再接続、二重送信防止 |
| データ | Web作成→Android表示、Android作成→Web表示、削除・編集・添付の相互反映 |
| 表示 | ライト／ダーク、文字拡大、日本語、長文、コード、数式、RTL候補、空状態 |
| 端末 | API 26、最新API、スマートフォン、タブレット、縦横、低メモリ復帰 |
| 安全性 | Cookie混入なし、別originへBearer送信なし、HTTPS限定、バックアップ除外、所有者検証 |
| 配布 | versionCode増加、固定fingerprint、debug/release成功、APK SHA-256、Release資産 |

## 10. 進捗更新ルール

- 機能を実装した版で、この文書の状態と「次の作業」を更新する。
- 新しいWeb機能を追加したら、Android実装の有無にかかわらず機能差分へ追加する。
- APIやUIのファイル配置が変わった場合は `README.md` の地図も更新する。
- 基準版は、検証済みのAndroid ReleaseとWebリリースに合わせて更新する。
- 未実装項目を削除して差分を隠さない。対象外にする場合は理由と代替導線を書く。
- 本書に詳細な通信ペイロードや署名手順を重複させず、`../deploy/ANDROID_CLIENT.md` を更新して参照する。
