# 検証の選び方と実行順序

着手前は `tests/README.md` の表から変更分野を選び、その文書だけを読んで関連テストと実装上の契約を確認します。テストの一覧を探すために全テストのソースを読む必要はありません。複数分野にまたがる変更では該当分野だけを組み合わせます。

## 実装後

対象を絞った実行はリポジトリのルートで行います。

```bash
venv/bin/python -m pytest -q tests/test_model_cost_estimates.py --tb=short
```

Webの通常公開では、ソース編集を終えて `scripts/prepare_version.sh --notes "公開向けの本文"` を実行します。スクリプトが現在の版でフロントエンドをビルドし、構文・資産・文書・全回帰テストを確認します。成功してから版番号、changelog、版付き資産を更新し、新しい資産を再ビルドして構文・参照を確認します。全回帰テストは版更新前の1回だけです。直前に別の全回帰テストを重ねる必要はありません。

公開しない検証には `scripts/verify_changes.sh` を使います。ソースをビルドする機能はないため、JS部品を変更した場合は先に `scripts/build_frontend.sh` を実行します。サーバーだけ・Androidだけ・運用だけの変更にWebの版上げ手順を使いません。[公開経路](../../scripts/docs/release_workflow.md) を参照してください。

Androidのコンパイル・テスト・lint・署名・配布はGitHub Actionsだけで実行します。ローカルのGradleやAndroid SDKは実行しません。

## 結果と失敗

成功時は件数と要約だけを読みます。失敗時は失敗名・エラー付近だけを読み、該当テストや実装の周辺に範囲を限定します。テストが保証する条件を確認するために、該当するテスト本体を読むことはできます。実装と無関係な期待値変更やテストの無効化で通してはいけません。

版更新前の検証で失敗した場合は、版番号とchangelogは変わりません。修正後に `prepare_version.sh` を再実行できます。版番号が既に更新された後の確認で失敗した場合は同スクリプトを再実行せず、修正・ビルド後に `verify_changes.sh` で確認します。

`verify.preflight.last.log` は版更新前、`verify.last.log` は通常の検証または版更新後の構文・資産確認のログです。全ログを通読しません。スキップされたテストを成功件数として報告しません。

長時間コマンドは最初からバックグラウンドで1回起動し、親シェルの `wait` またはツールの実行セッションで終了を受け取ります。タイムアウトだけを理由に起動し直しません。`nohup ... &` だけで親シェルを終了させる方法は、実行環境によって子プロセスも終了するため使いません。

## スキップと隔離

テスト省略は明示された場合だけです。`prepare_version.sh --skip-verify` は回帰テストを省き、版更新前後の構文・資産確認は実行します。更新後作業全体をスキップする指示では同スクリプトや検証・Git操作も行いません。

`conftest.py` と `verify_changes.sh` はpytestを隔離したSQLiteへ向けます。実運用のDB・APIキー・利用者データをテストに使いません。実画像が必要でもPillowは使わず、既存の画像ヘルパ・ffmpeg・定数を使います。

## 文書の維持

テストを追加・削除・改名・分割したら、該当分野の一覧も同じ変更で更新します。保証する契約が変わった場合もその文書を更新します。ファイルは分野・責務ごとに分け、新分野のテストを既存の大きなファイルへまとめて追記しません。`test_prepare_preflight.py` が索引の漏れとリンク切れを確認します。
